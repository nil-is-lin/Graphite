# ADR-006: Inline LaTeX Math in the Text Node (source-canonical, bake-to-Vector)

## Status
Proposed

## Context
ADR-005 delivered TikZ *export* — Graphite can emit its vector artwork as LaTeX. The natural complement is letting users *author math/equation content inside Graphite* as editable text. The requirement, clarified by the user, is **not** a separate equation node but **inline `$...$` / `$$...$$` math environments inside the existing Text tool's content**.

Graphite's document is a compiled node graph whose leaf geometry is `Vector` (Bézier `Subpath`s + `DAffine2` transforms), consumed by three renderers: `SvgRender`, `TikzRender` (ADR-005), and the raster/Vello path. Any content that presents itself as a `Vector` inherits SVG + TikZ + raster export for free, with **zero** changes to those renderers.

The existing Text node already bakes text to `Vector` at a single seam: `text-nodes::to_path::shape_text_item(item: &Item<String>) -> List<Vector>`, which calls `TextContext::to_path` (Parley layout) and applies transform/blend/opacity. This is the natural injection point.

The core unsolved problem is therefore narrow and well-bounded: **LaTeX source string → Bézier `Vector`**, spliced into the text flow. Everything else (export, display, transforms) already exists.

The bake step (LaTeX source → SVG `<path d>` → `Vector`) is isolated behind `bake_math_span`, so the *engine* is a swappable implementation detail, not a fork in the architecture. Three candidate engines were weighed (see planning discussion), and the decision is a **runtime engine selector** rather than a single hard-wired engine:

- **Web/browser target → MathJax (JS, SVG output).** The webview engine that bakes LaTeX to SVG `<path>` data. **Correction (2026-07-22):** the plan originally named **KaTeX** here, but KaTeX only emits HTML + webfont glyphs — it has *no* SVG output mode, so it cannot produce the `<path d>` geometry Graphite needs to bake into `Vector`s. MathJax (with its `tex-svg` component) is the browser-side engine that actually emits SVG paths. It is ~1.8 MB and loaded lazily (dynamic `import`) only when `$...$` is first typed. **Zero Rust compile cost.** Chosen as the engine for any context that already has a webview.
- **Native/headless target → `typst` + `mitex` (Rust CLI, preferred when available).** `mitex` (`@preview/mitex`) is a Typst *package* that parses LaTeX **math-mode** source directly into Typst math. The bake wraps the source in a tiny `.typ` document — `#import "@preview/mitex:0.2.7": mi` + `#mi("<source>")` — and calls `typst compile --format svg`. This is **Rust-native end to end**, fully headless, and needs only the `typst` binary (no pandoc, no TeX Live). It is the user's preferred native engine.
- **Rejected: `pandoc` + `typst`.** Pandoc's typst writer *can* transpile LaTeX→Typst, but pandoc is a *separate binary* (not embeddable as a crate) — so this path needs **two** external binaries (pandoc *and* typst) and reintroduces pandoc's weight. `mitex` achieves the same LaTeX-math→Typst result with **one** binary (`typst` only) and no pandoc. Rejected in favor of `typst`+`mitex`.
- **Rejected: bundled Rust TeX engine (`tectonic`/`typst` *crate*).** Highest fidelity but +100 MB (tectonic) or a heavy *compile-time* dependency (`typst` crate) that re-inflates the build graph. Tectonic also has **no native SVG output** (only `pdf`/`xdv`/`html`), forcing a `dvisvgm`/`pdf2svg` step. Worst of both worlds. The `typst` *CLI* used by the mitex path avoids the crate's compile cost — it is a runtime dependency, not a Cargo dependency.

A standalone `EquationNode` was considered first but **superseded** by inline math spans (same bake-to-Vector mechanism, embedded in the Text node, inherits editing/transform/export for free).

## Decision
Extend the **existing Text node** (no new node type) so its content string is segmented into spans:

- `Plain(String)` — shaped by the existing `to_path` (Parley) pipeline, unchanged.
- `InlineMath(String)` — `$...$`, baked to a `Vector` and flowed within the surrounding line as an atomic, non-breaking graphic, baseline-aligned to the text.
- `DisplayMath(String)` — `$$...$$`, baked to a `Vector` and forced onto its own block (line break before and after).

The segmentation is implemented as a **pure Rust parser** (`text-nodes::span::parse_text_spans`, P0) with no Parley/font dependency, so it is unit-testable in isolation and reusable by the frontend for live preview. Rules: `\$` is a literal dollar; an opener with no matching closer degrades to literal text (graceful, no panic); display and inline closer detection are mutually exclusive (`$$` never closes inline, a lone `$` never closes display).

**Where the bake runs (engine selector, the integration seam):** `bake_math_span` picks an engine per runtime environment, but the *output contract* is identical everywhere — SVG `<path d>` → `Subpath`/`BezierHandles` → `Vector`, committed into the document keyed by a **source hash** (the derived cache). Because the `Vector` is materialized, headless export (CLI / `graphene-cli`) works without a live webview.

- **Browser / desktop webview:** run **MathJax** in the frontend (lazy-loaded `tex-svg` component). On edit it produces SVG `<path d>`; the `<path d>` is sent to Rust via the existing message channel. The frontend is the **anti-corruption layer** between MathJax and Graphite's `Subpath` model.
- **Native (headless CLI), `typst` present:** run `mitex` via `typst compile --format svg` (launched as a subprocess). No webview needed.
- **Native, `typst` absent:** degrade to the **placeholder bake** (raw LaTeX source shaped as ordinary text, from P1) — never panic, the document still renders something. (MathJax is *not* a fallback here: it needs a webview, which a headless CLI lacks.)
- **Desktop, no `typst`:** MathJax via the webview (same as the browser path) is the fallback.

Detection is a cheap runtime probe (`command -v typst` / feature flag); the result is cached per session. All branches converge on the same `Vector`, so `math_bake` / the concatenator / the three renderers are untouched regardless of which engine actually fired.

A new **flow concatenator** (P1) reuses `to_path` for plain spans and splices the baked math `Vector`s, performing a small line-break/alignment pass (x-advance, wrap at `max_width`, per-line alignment, baseline alignment of math to text). Its output is `List<Vector>` — identical to today's, so `SvgRender` / `TikzRender` / raster are untouched.

## Consequences

### What becomes easier
- Math is authored inline within the Text tool — the most natural UX, no separate node to manage.
- SVG + TikZ + raster/PNG export of math come for free (it's just a `Vector`).
- No TeX engine in the Rust *Cargo* graph: MathJax is JS in the webview (lazy-loaded), and the typst path uses the `typst` **CLI** (a runtime binary), not the `typst` *crate*. So **zero Rust compile-time cost** — consistent with ADR-005. (If we ever `cargo add typst`, this advantage disappears; we deliberately keep typst as a CLI.)
- Editable: re-running MathJax from `source` re-bakes the paths.

### What becomes harder / trade-offs (named)
- **Source-canonical vs headless.** Storing only `source` keeps files small/editable but needs MathJax at edit time; storing the baked `Vector` makes headless export trivial but bloats files. **Decision: store both** — `source` is canonical and always persisted; the baked `Vector` is a derived cache (invalidated by source hash). Cost: a re-bake step on edit/load.
- **Engine availability for authoring.** Browser/desktop author via MathJax (webview, SVG output); headless CLI authors via the `typst`+`mitex` subprocess. If *neither* is present, a headless CLI can only *render* math already baked into the document, not *author* a new formula. Acceptable — authoring is inherently interactive, and the baked `Vector` keeps export working everywhere.
- **Loss of LaTeX semantics after baking.** Once math is a `Vector`, you cannot restyle it per-glyph as LaTeX without editing `source`. Same constraint as all text.
- **Line-breaking limitation (v1).** Math spans are atomic and non-breaking; `$$` forces its own block, and an inline span wider than the remaining line wraps the whole formula to the next line. Finer in-formula wrapping is deferred.
- **LaTeX math-subset coverage.** Both MathJax and `mitex` cover the vast majority of LaTeX *math-mode* macros but not every package; exotic macros degrade (no render). Acceptable for v1. The engine is swappable, so coverage can be widened later by adding an alternative bake (e.g. a `typst`/`tectonic` crate) behind the same `bake_math_span` seam.

### Implementation phases
- **Phase 0 — Span parser (DONE).** `text-nodes::span` splits Text content into `Plain`/`InlineMath`/`DisplayMath` with `\$` escaping and unmatched-delimiter fallback; covered by unit tests. No engine, no renderer change.
- **Phase 1 — Bake boundary + flow concatenator (DONE, Rust-only, no MathJax yet).** `text-nodes::math_bake::shape_text_item_with_math` parses spans, shapes plain spans via the existing `to_path`, bakes math spans via a placeholder `bake_math_span` (P1: shapes the raw LaTeX *source* as ordinary text so the full span→bake→splice flow is exercised with zero new deps), then concatenates via a lightweight flow pass: x-advance between inline spans, forced line-break around `DisplayMath`. Outer transform/blend/opacity are applied once to the concatenated result. `Text to Vector` / `Text to Vector Glyphs` now route through it. Proven by unit tests (inline advances `x`; display breaks the line; unmatched `$` degrades without panic). A source-hash `MathCache` is deferred to P4 (serialization) — the bake signature is unchanged when P2 swaps in MathJax.
- **Phase 2 — Engine integration (selector).** `bake_math_span` implements the runtime selector: cache → native `typst`+`mitex` subprocess (`typst compile` → SVG → `svg_path_to_bezpath` → `Vector`, scaled to font size via the shared `normalize_to_font_size` helper) → placeholder (source-as-text). **DONE & verified (native)**: `cargo test -p text-nodes` real-bakes `\frac{a}{b}` via the installed `typst` 0.15 + `@preview/mitex:0.2.7` into a `Vector` whose height tracks the font size. **Fix (2026-07-22):** `typst compile --format svg` emits a full-page white background rectangle and places glyphs via `<use xlink:href="#symbol">` references. The naive regex extractor captured the background rect as geometry, which rendered as a solid black box once the text layer's fill was applied. `extract_path_d` was replaced with a `usvg`-based parser that resolves `<use>` references, applies absolute transforms, and skips the page-background rectangle. **P2b (frontend MathJax feed) IMPLEMENTED**: a new wrapper command `cacheBakedMath(source, font_size, svg_paths)` → `text_nodes::math_bake::cache_baked_math_svg` parses the MathJax SVG `<path d>` strings and normalizes them into the cache. The frontend (`frontend/src/utility-functions/math-bake.ts`) ports `parse_text_spans` to TS, runs **MathJax v4** (`tex-svg.js`, loaded lazily via dynamic `import`) on each math span and converts it with the v4 API `MathJax.startup.document.convertPromise(tex, { display })`, extracts the `<path d>` (skipping `<clipPath>`), and feeds Rust; it is hooked into the Text tool's commit (`triggerTextCommit`) and live-input (`oninput`) handlers in `Document.svelte`. **Engine-API note (2026-07-22):** MathJax **v4 removed the v3 `tex2svg`/`tex2svgPromise` globals**; the correct v4 browser call is `MathJax.startup.document.convertPromise(tex, { display })`, and `svg.fontCache` must be `"none"` so glyphs are emitted as inline `<path d>` rather than `<defs>`+`<use>` references. **Verification caveat:** the frontend path requires a full app build to run-verify (the wasm-wrapper regenerates `cacheBakedMath` into the `EditorWrapper` types, and `mathjax` is now an npm dependency); Rust side (`cargo check -p graphite-wasm-wrapper --features editor,native` + `text-nodes` tests) passes. The native `typst` path remains the headless/default on machines with `typst`; the MathJax path covers web/desktop-webview where `typst` is absent (and is hardened so it also works when the app is launched from Finder, where homebrew's `/opt/homebrew/bin` is off `PATH`).
- **Phase 3 — Live preview in the Text tool overlay (DONE, frontend-only).** A non-interactive preview element (`math-bake.ts::renderMathPreview`) typesets each math span with MathJax v4 (`tex-svg.js`, `convertPromise`, SVG output) and escapes plain text, producing HTML shown in a `.text-preview` strip anchored above the editable textbox via the same document transform (shifted up by its own height, so it never overlaps the raw source). It refreshes on `displayEditableTextbox` (seed), `oninput` (live), and `triggerTextCommit` (final). This is the literal "show typeset math inline while editing" — the user sees the formula as they type, while the raw `$…$` source stays editable in the box below. **Trade-off named:** the preview is a strip above the box, not an in-contentEditable inline replace (true caret-aligned inline rendering would require measuring spans inside the editable element — high complexity/risk for an optional phase). The committed canvas result already shows the baked `Vector` via the existing commit path. **Verification caveat:** frontend run-verification needs a full app build (same as P2b).
- **Phase 4 — Caching & serialization (DONE).** The bake cache was **refactored from `(Vec<Item<Vector>>, f64)` to `Vec<String>` (raw SVG path `d` strings)** — engine-agnostic and *font-size-independent*, so one entry serves every text node at its own font size (this also fixed the pre-refactor bug where geometry was cached at the first-seen font size only). `bake_math_span` now normalizes the stored paths to a `Vector` at the requesting node's font size on each use. `export_cache()` / `import_cache()` snapshot and merge the cache. The cache is **persisted into the document** as `DocumentMessageHandler::math_bake_cache: HashMap<String, Vec<String>>` (serialized via `serde_json`, `#[serde(default, skip_serializing_if = empty)]` so old docs still load). On **save**, `document.math_bake_cache = math_bake::export_cache()` is set before `serialize_document()`; on **load**, `deserialize_document` calls `math_bake::import_cache` to repopulate the process-wide cache. **Consequence:** documents reopen with typeset math intact even with no bake engine present (headless/CLI export, offline) — the persisted paths normalize on load. **Known limitation:** `export_cache` dumps the *process-wide* cache (may include entries from other open documents); on load those extra entries are harmlessly merged. Verified: `cargo test -p text-nodes` (23 passed), `cargo check -p graphite-editor` (adds `text-nodes` dep + the field/hooks). TikZ/SVG/raster export already emit math as paths (ties back to ADR-005).

## Alternatives Considered (engine for the bake step)
- **MathJax (chosen webview engine):** emits real SVG `<path>` geometry, broad LaTeX coverage. Limitation: ~1.8 MB (lazy-loaded, so only fetched when `$...$` is first used) and asynchronous; needs a webview, so not usable for headless authoring. **Note:** KaTeX was the *original* plan but was rejected for the bake step because KaTeX has **no SVG output** (HTML/webfont only) — it cannot produce the `<path d>` Graphite bakes into `Vector`s. KaTeX remains a fine *preview-only* renderer but is unsuitable as the geometry source.
- **`typst` + `mitex` (chosen native, preferred when present):** Rust-native, headless, one binary, parses LaTeX math directly. Limitation: needs the `typst` CLI at runtime; first compile fetches `@preview/mitex` (bundle/pre-warm for offline/CI); covers math-mode only (fine for inline math).
- **`pandoc` + `typst` (rejected):** same end result as mitex but needs *two* binaries and pandoc is not embeddable as a crate — heavier, no benefit over mitex.
- **`tectonic` (rejected):** complete LaTeX but +100 MB and **no native SVG output** (extra `dvisvgm`/`pdf2svg` step); also not embeddable cheaply.
- **`typst` *crate* (rejected for v1):** would add a heavy compile-time dependency to the already-slow build graph; kept as a runtime CLI instead.
- **Standalone `EquationNode` (superseded):** replaced by inline spans in the existing Text node (less surface, inherits Text editing/export).

## Reversibility
Fully additive: a new `span` module + a flow-concatenator function + (frontend) MathJax `tex-svg` call + a small SVG-path parser. Removing the feature means deleting `span.rs`/the concatenator and the UI hook; no existing renderer or document type is touched. Low risk, reversible. The only new Rust component with any weight is the SVG `<path d>` → `Subpath` parser (P1), which is independently useful (future SVG import) and small.

## Verification
- **Unit (P0, DONE):** `cargo test -p text-nodes span` — covers plain-only, inline, display, `\$` escape, unmatched-delimiter fallback, backslash preservation inside math, and consecutive spans.
- **Unit (P1, DONE):** `cargo test -p text-nodes math_bake` — `no_math_delegates_to_single_compound_vector` (fast path unchanged), `inline_math_advances_x` (concatenator advanced `x` past the math span), `display_math_breaks_onto_its_own_line` (vertical extent exceeds a single line), `unmatched_dollar_degrades_to_plain_without_panic`, and `merge_vectors_produces_single_vector` (single-`Vector` output path).
- **Integration (P2):** in the frontend, type `$E=mc^2$` inside a Text layer, confirm MathJax SVG → `Vector` → on-canvas render, and export to `.svg`/`.tex` shows the typeset math inline.
- **Integration (P2, native) — DONE:** `bake_math_span("\\frac{a}{b}", item)` with `typst` installed returns a non-empty `Vector` whose height tracks the font size (test `real_bake_scales_to_font_size_when_typst_present` passes). The SVG `<path d>` parser (`svg_path_to_bezpath`) is covered by `svg_path_to_bezpath_parses_basic_shapes`. Downstream flow/export (SvgRender / TikzRender / raster) are shared and unchanged.
